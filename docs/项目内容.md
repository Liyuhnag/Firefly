## 版本一：AI 应用开发

**智能运维助手（ChatOps Agent）｜AI 应用开发｜2026.XX–2026.XX**
**技术栈：** Python / Django / DRF / Celery / Redis / MySQL / LangGraph / MCP / 蓝鲸体系（日志平台 / 监控平台 / API Gateway）/ 企业微信机器人 / Langfuse

**项目简介：** 面向运维团队“信息散落在多个系统、靠人登录翻找拼装”的现状，以企业微信群聊为入口构建运维智能体，将取日志、查服务器文件、跨库取数、告警多指标分析等高频操作收敛为一句话请求，并自动产出修复方案与复盘报告，按工具风险等级分级授权执行；向上游接住运营的取数需求，向下游将分析结论交付开发做代码级检查。**【待填：覆盖场景数 / 单次请求响应由 XX 缩短至 XX / 修复方案产出由 XX 缩短至 XX】**

**项目亮点：**

- **多 Agent 编排与上下文治理：** 日志与查询结果体积大，Agent 间传递完整原始内容会造成上下文膨胀并干扰判断；基于 LangGraph 编排任务节点，节点间仅传递筛选结果、研判结论等结构化产物，原始日志按需从工具层拉取，并接入 Langfuse 追踪节点输入输出、耗时和 Token 消耗；单次对话 Token 消耗降低 **30%**【待确认口径】。
- **分层意图识别与模型路由：** 群聊请求是口语化短句，且常以“引用上一条消息”的形式给出，环境、时间、目录、服务器等关键参数大量缺失；全部交由强模型处理会增加成本和延迟，轻量模型又难以解析复杂条件；设计“规则→轻量模型→强模型”三级识别机制，按置信度升级，并将口语化表述转为结构化参数；意图识别准确率达 **92%**【待确认评测集】，强模型调用量减少 **60%**【待确认】。
- **修复方案规划与双层审核：** 告警处置往往涉及多个动作，直接执行可能引发次生故障；规划 Agent 将处置过程拆解为任务 DAG，先由**审核 Agent 做机器校验**——逐个校验动作的影响范围、是否命中核心服务保护规则、是否预置回滚，不通过则触发重新规划；机器审核通过后再**交人工审核**（见下条）。机器审核先行的目的是把明显不合格的方案过滤掉，让人只对剩下的高风险项做决策。**【待填：方案产出由 XX 缩短至 XX / 机器审核拦截率 / 一次采纳率】**
- **可恢复的人在回路：** 运维收到修复方案后有时当场确认、有时隔数小时才回复，期间服务还可能重启；中断必须落在检查点边界上——预置 Agent 把循环藏在框架内部、边界不可控，手写 ReAct 循环把所有步骤塞进单个节点、节点内没有检查点（恢复会导致模型重跑、已执行的工具再执行一次）；因此将循环本身拆成图，模型调用、审批、工具执行各是一个节点，中断只发生在审批节点，恢复时只重跑这一个只读节点；基于 LangGraph `interrupt` / `Command(resume)` 与 MySQL 检查点实现长时间挂起与断点续接。**【待填：最长挂起时长 / 恢复成功率】**
- **MCP 工具接入与风险分级治理：** 日志平台、业务库、服务器、监控平台协议各异，逐个对接成本高；通过 MCP 统一接入外部工具，但 MCP 协议本身不定义授权粒度，因此在 Agent 侧按 tool name 建立风险等级注册表（L0 只读 / L1 低危 / L2 高危 / L3 禁用），调用时按等级走不同授权流程——L0 直接调用、L1 默认执行可群里否决、L2 必须逐条确认、L3 拒绝生成；L1 / L2 工具必须预置回滚方可注册，等级只能调高不能调低；新工具接入由 **3 天缩短至半天**【待确认】。

## 项目亮点

- **故障后的知识辅助检索：** 知识库不直接生成故障根因，而是在故障分析后，根据分析结果检索相似历史案例、相关解决方案及支持证据；返回 SOP 章节、置信度等来源信息，为后续判断和处置提供可追溯参考，并支持结构化 JSON 与 SSE 流式问答两种响应模式。
- **多格式文档解析与图片内容检索：** 针对 SOP、历史案例格式多样，且拓扑图、配置截图等图片信息难以检索的问题，使用 **MinerU** 解析 PDF、DOC、Excel、MD 等文档，保留标题层级和表格结构；调用 LLM 为图片生成语义描述并纳入索引，使文档文本与图片内容均可检索。
- **文档异步处理与大文件断点续传：** 针对文档上传、解析、切片、向量化流程较长，以及大文件上传中断后需要恢复的问题，使用 **Kafka** 将处理环节拆分为后台任务，通过 **Redis Bitmap** 管理分片上传状态，并结合 **MinIO** 实现断点续传，提升文档处理链路的可恢复性与吞吐能力。
- **多路查询路由：** 针对 SOP 处置步骤、报错码和历史 Incident 的查询特征差异，基于 LLM 意图识别与 few-shot 示例，将查询路由至 Elasticsearch（BM25 + 向量混合检索）、MySQL（Text2SQL）或 Neo4j（Text2Cypher），支持单路及多路并行检索，并在路由失败时自动降级；意图识别准确率达 **98%**。
- **RAG 召回质量优化：** 针对固定长度分块可能截断处置步骤、单一向量召回对专业术语和报错码命中不足的问题，引入滑动窗口重叠、父子分段、Query 改写、BM25 与向量混合召回及 Reranker 精排；召回完整度由约 **75% 提升至 90% 以上**，Top-5 召回率由 **82% 提升至 96%**。
- **RAG 评估体系建设：** 针对检索与生成效果缺少统一量化标准的问题，构建 **400+** 测试问题集，结合 Ragas 的 faithfulness、context_recall、answer_relevancy 指标与人工抽检，形成策略变更可量化验证、效果问题可持续迭代的评估流程。

其中“日均处理 5 万+ 条告警、支撑 400+ 个 Incident、根因定位由小时级缩短至分钟级”是**平台整体成果**，可以放在项目简介中，但不要归为知识库模块的个人指标。
