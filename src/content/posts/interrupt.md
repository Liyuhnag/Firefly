# 项目实现 Human-in-the-Loop 抉择

在运维场景里，模型给出的资源调整方案不能直接落到生产环境：高危变更需要人确认，而确认可能要等几小时，期间服务还可能重启。这就要求"中断 → 持久化 → 长时间挂起 → 恢复"是一条完整链路，而不是一次性的阻塞等待。

## 架构选择

|         框架          |             HITL 机制             |     状态持久化      |         流式兼容         | 长时间挂起 | 断点续传 |
| :-------------------: | :-------------------------------: | :-----------------: | :----------------------: | :--------: | -------: |
|     **LangGraph**     | `interrupt()` / `interrupt_after` |    ✅ Checkpoint     | ⚠️ `interrupt_after` 可以 |     ✅      |        ✅ |
|   **LangChain 1.0**   |     HumanInTheLoopMiddleware      | ✅（依赖 LangGraph） |          ⚠️ 同上          |     ✅      |        ✅ |
|      **AutoGen**      |          UserProxyAgent           |       ❌ 内存        |            ❌             |     ❌      |        ❌ |
|       **Dify**        |            工作流节点             |      ✅ 数据库       |            ✅             |     ✅      | ⚠️ 节点级 |
| **OpenAI Agents SDK** |              Handoff              |          ❌          |            ❌             |     ❌      |        ❌ |
|     **OpenClaw**      |         Skills + 聊天异步         |      ❌ 需自建       |        ✅ 天然异步        | ✅ 聊天等待 | ❌ 需自建 |

真正支持"中断 → 持久化 → 长时间挂起 → 恢复"完整链路的，目前只有 **LangGraph（及依赖它的 LangChain 1.0）** 和 **Dify**。我们的系统跑在 LangGraph 上，选择 Checkpoint 方案是自然的。

## Agent 内部选择

### 第一轮：直接用 LangChain 的预置 Agent

LangChain 提供 `create_agent`（原 `create_react_agent`）和人工审批中间件，配置危险工具名单就能中断，看起来最省事。

放弃的原因是内部不透明，和项目的追踪与分层冲突。详见 ADR-003，和本需求直接相关的有三点：

- 循环在框架内部。每次模型调用、工具调用要记一条带模型名、提示词版本、上下文规则版本、输入指纹、token 数的 Span，只能从回调事件里间接取，字段位置随版本变化，提示词版本和上下文规则版本回调拿不到。

- 中间件只认 LangChain 的消息和工具类型。项目已经统一使用自己的 `Message`、`ToolCall`、`Tool`、`ChatModel`，接入就要两套类型来回转换，输入指纹也要保证两边一致。

- 中断的载荷、拒绝后的处理、恢复值的格式由中间件决定。审批卡片要展示什么、拒绝后给模型什么提示，都要去适配它的约定。

### 第二轮：在一个节点里手写 ReAct 循环

按 ADR-003，循环自己写：Agent 的 `execute()` 里一个 `while`，调模型、执行工具、追加消息，整个 Agent 作为一个 `AgentNode` 挂进对话图。追踪问题解决了，但人工审批做不了。

如果在循环里、执行危险工具之前调用 `interrupt`：

- 恢复时整个节点从头重跑，`execute()` 从第一次模型调用开始重来。
- 模型调用不确定。重跑时模型可能选另一个工具，或者换了参数，用户批准的和实际执行的不是同一个。
- 中断之前已经执行过的工具会再执行一次。只读工具浪费时间，写操作就是事故。
- 已经推给用户的正文、进度、Span 会再推一遍、再记一遍。

试过两种补救，都不成立：

- **按 `tool_call_id` 在状态里缓存工具结果，重跑时命中就跳过。** 模型重跑后生成的 `tool_call_id` 和参数都可能不同，缓存命中不了；即使命中了，模型调用本身仍然重发。
- **在 `execute()` 里自己把对话中间状态存起来，恢复时跳到断点。** 等于在节点内部再实现一遍检查点和断点续跑，正是 ADR-003 里决定不自己写的那部分。

结论：中断只能在节点边界之后安全使用。手写循环把所有步骤放在一个节点里，节点内部没有检查点，也就没有可以安全中断的位置。

### 第三轮：把循环本身拆成图

具体做法是：模型调用、审批、工具执行各是一个节点，循环是边。每个节点结束时 LangGraph 写一次检查点，模型的决定在进入审批之前已经落盘。中断只发生在审批节点，恢复时只重跑这一个节点，而它只读状态、调用 `interrupt`，重跑没有代价。

这也是 LangGraph 自带的预置 Agent 和审批中间件内部的做法。区别是节点由我们自己写，模型、工具、消息、Span 全部沿用现有实现，第一轮的问题不会回来。

另一个考虑过的做法是 LangGraph 函数式接口的 `@task`：保留 `execute()` 的命令式写法，把每次模型调用和工具调用包成 task，恢复时已完成的 task 直接返回检查点里的结果。没有采用，因为 task 之外的推送和 Span 仍会重复，需要另做去重；流式模型调用也不适合包成 task；而且这要求 `agents/` 依赖 LangGraph，违反 ADR-003 的分层。

## 小结

回顾这三轮，真正的约束其实只有一条：**中断点必须落在检查点边界上**。预置 Agent 把循环藏在框架里，检查点边界不可控；手写循环把所有步骤塞进一个节点，节点内没有边界；把循环拆成图之后，每个节点结束都会落盘，审批节点本身只读状态、没有副作用，重跑才变成零成本的事。剩下的选型，不过是这条约束之下的工程取舍。
