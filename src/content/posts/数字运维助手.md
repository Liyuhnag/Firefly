# 数字运维助手

> **定位**：一个 IM 原生的运维智能体。入口在群聊，做的是代替运维登录各个系统去取数、研判、产出结论，并按工具风险等级分级授权执行。
>
> 主用户是运维。运营和开发不直接使用它，而是站在同一条链路的两端：运营的取数需求先到运维，运维取完数再回答运营；运维的分析结论产出成报告，交付给开发做代码级检查。

## 背景

这个工具的主用户只有一类人：**运维**。

运营和开发并不直接使用它，而是站在运维这条链路的两端：

- **上游**：运营要数据，需求先提给运维，运维取完数再回答运营；
- **自身**：运维自己日常的取日志、查文件、告警分析；
- **下游**：运维把分析结论产出成报告交付开发，开发据此触发 skills 做代码检查。

三类场景共用同一套能力，区别只在背后接的信息源。

### 上游：替运维接住运营的取数需求

运营想调某个用户的行为信息（登录、交易、赠送、言论等），需求照例提给运维。

- **过去**：运维要么自己跨登录表、交易表、赠送表、言论表写 SQL 查，要么把需求转给开发同学，等开发查完再反馈给运营——一次取数要跨两个人、等一轮排期。
- **现在**：运维在群里一句话说明要什么，Agent 直接跨表取数并汇总，运维当场就能回复运营。

省掉的不只是写 SQL 的时间，更是"运维 → 开发"这一次转手。

### 运维自身：三类高频动作

#### 取日志

项目组提出"把测试环境昨天 21 点的日志发一下"：

- **过去**：日常进程日志可以走蓝鲸体系的 BKChat 或标准运维的自动化流程触发；不常用的日志则要运维登录 Windows 服务器，下载到本地后再发到群里。
- **现在**：运维在群里艾特它复述请求，或者直接引用上一条消息，日志由工具直接发到群里。

#### 查文件

第二天要发版本，研发提交了修复版本，QA 上线测试后却发生宕机，项目组会立即追问指定服务器、指定目录中的文件是否已经就位：

- **过去**：运维登录机器确认，再回群答复。
- **现在**：在群里直接呼叫查询服务器文件，当场答复。

#### 告警分析

监控平台触发告警后：

- **过去**：只有运维人员人工同时比对多个指标才能得出结论，处理完还要手写复盘报告。
- **现在**：把告警信息交给 Agent，它自动分析多个指标，生成统一的修复建议，并产出复盘报告。

### 下游：把结论交付给开发

线上系统出问题（例如定时任务不启动），排查链路通常是"日志 → 结论 → 代码"：

- **过去**：开发自己进日志平台捞日志、做分析，从海量日志里找线索，起点很低。
- **现在**：运维先用 Agent 完成日志分析，产出一份已经收敛到大致范围的分析报告交给开发；开发从这份报告出发，直接触发 skills 做代码级检查，配合 MCP 定位具体代码问题。

开发拿到的不再是原始日志，而是一份结论——排查的起点从"翻日志"前移到了"查代码"。

## 落地方向

五个场景、一条链路，看起来很散，但抽象出来是同一件事：**运维想要一个结论，而这个结论散落在好几个系统里，得靠人登录、翻找、拼装、判断。**

| 场景         | 信息散落在哪                     | 过去的成本                     | Agent 要做的       |
| :----------- | :------------------------------- | :----------------------------- | :----------------- |
| 应答运营取数 | 登录表、交易表、赠送表、言论表等 | 运维自己写 SQL，或转给开发同学 | 取数 + 汇总        |
| 运维取日志   | 标准运维流程 / Windows 服务器    | 找流程，或登录机器下载再发群   | 取数               |
| 运维查文件   | 指定服务器的指定目录             | 登录机器确认                   | 取数               |
| 运维告警分析 | 监控平台的多个指标               | 人工同时比对多个指标 + 手写复盘 | 取数 + 研判 + 产出 |
| 交付开发     | 日志平台 + 代码仓库              | 开发自己捞日志从零分析         | 研判 + 产出        |

真正的共性不是某一个系统，而是**跨系统的信息获取与研判**：入口统一在群聊里，背后是散落各处的信息源。

### 结论：落在「取数 → 研判 → 产出 → 受控执行」

- **取数（Retrieve）**：用一句话把原始信息从日志、数据库、服务器、监控平台、代码仓库里取回来。这一步是纯工具调用，也是五个场景共有的部分。
- **研判（Reason）**：把多源信息交叉比对，得出人原来要自己做的那个判断——告警到底是什么原因、代码哪里有问题。
- **产出（Deliver）**：把结论加工成能直接用的东西，比如复盘报告、以及一组按风险等级标注的修复动作。
- **执行（Execute）**：只执行授权范围内的工具调用，L1 / L2 自带回滚，结果逐条反馈。

### 为什么不适合叫"可观测助手"

可观测性（Observability）有明确边界：metrics / logs / traces 三支柱。对照下来只有两个案例落在这个圈里——取日志（logs）和告警分析（metrics）。

而运营要的是**业务数据查询**，运维查服务器文件是**主机状态查询**，交付给开发的则是**研发诊断**。这三个都不属于可观测。叫"可观测助手"等于把一半的场景排除在名字之外，范围被自己说窄了。

所以它不是"可观测工具"，而是一个 **IM 原生的运维智能体**：入口是群聊，能力是代替人去各个系统里跑腿、做初步判断，并按工具风险等级分级授权完成修复动作。

### 执行边界：按工具风险等级分级授权

外部工具通过 MCP 接入。但 MCP 只解决"能不能调通"，不解决"该不该让它调"——协议本身不定义授权粒度，外部 Server 的实现我们也改不了。所以风险分级是自建的一层治理：工具接入之后，按 **tool name** 在注册表里标注等级，调用时按等级走不同的授权流程。

| 等级    | 含义                   | 授权方式                   |
| :------ | :--------------------- | :------------------------- |
| L0 只读 | 查询类工具，不改变状态 | 无需授权，直接调用         |
| L1 低危 | 可逆的轻量写操作       | 默认执行，运维可在群里否决 |
| L2 高危 | 影响服务可用性的写操作 | 必须运维逐条确认           |
| L3 禁用 | 命中核心服务保护规则   | 拒绝生成，不进入方案       |

这么设计的原因：

- **风险是工具的属性，不是单次方案的属性。** 工具是有限集、可枚举的，tool name 就是它的稳定标识。按 tool name 定级，既不用每生成一份方案都重新评估，也不会出现"这次判成低危、下次判成高危"的摇摆。而且定级是新工具接入时的一次性动作，之后每次调用自动走对应流程。
- **授权粒度跟着等级走，而不是一刀切。** L0 必须完全不打断人——否则每查一次日志都要点一次确认，ChatOps 的效率优势反而被自己吃掉；L2 必须逐条确认——否则一次误操作就是事故。真正需要人介入的只有 L2 这一层。
- **禁用规则前置到工具层。** 核心服务保护不是"执行前再检查一遍"，而是这类调用根本不会出现在方案里，从源头杜绝。

配套的三条硬约束：

- 注册为 L1 / L2 的工具必须**预置回滚**，拿不出回滚方案的不允许注册；
- 执行结果**逐条反馈**，某一步失败即中止后续步骤，不做部分成功的静默处理；
- **等级只能调高不能调低**——线上跑一段时间后某个 L1 工具出了问题，先升到 L2，稳定运行后再评估是否降回。

### 落地节奏

顺着场景的确定性和风险排：**先只做取数，再做研判，然后做产出，最后放开受控执行。**

取数是最确定、风险最低、也最容易验证的一层——答案对不对一眼就能看出来，而且错了没有任何副作用。等取数稳定了再往上叠研判；研判的输出可信度积累够了，才谈得上自动生成复盘报告这类产出物；执行放在最后，且必须建立在工具分级授权和回滚机制完备的基础上。读链路可以先跑起来，写链路要等机制齐了再开。
