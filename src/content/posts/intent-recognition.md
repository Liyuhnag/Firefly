## 什么是意图识别

意图识别，就是判断用户**到底想做什么**。

它的输出通常由两部分组成：

- **意图**：一个预先定义好的枚举值，比如 `product_recommendation`、`order_query`；
- **参数**（槽位）：该意图执行所需的补充信息，比如商品类目、预算上限、使用场景。

一次典型的意图识别输出大概长这样：

```json
{
  "intent": "product_recommendation",
  "slots": {
    "category": "手机",
    "budget_max": 3000,
    "usage_scenario": "拍照"
  }
}
```

> [!IMPORTANT]
> 意图识别不是为了给用户输入贴标签，而是为了决定 Agent 后面**应该怎么想、加载什么上下文、调用什么工具、进入哪个业务流程**。

## 意图识别应该放在哪个阶段

按照识别发生的时机，可以分成三种做法。

### 做法一：和输入规范化合并进行

系统在做用户输入规范化时（纠正错别字、补全指代、整理成结构化表达），顺手把意图也识别出来。

这种方式在简单系统、小型 Agent、领域专属 Agent 中比较常见——反正输入本来就要洗一遍，多输出一个字段成本很低。

### 做法二：在进入主循环之前独立识别

用户输入进来后，系统先判断意图，再根据意图加载对应的 Spec、上下文和工具，最后才进入 ReAct / TAO 循环（Thought 思考 → Action 行动 → Observation 观察）。

这是工程实践中最主流的做法：**先分类，再执行**。

### 做法三：在主循环内部完成

让意图识别直接在 ReAct / TAO 循环里发生。模型一边思考，一边决定任务方向。

这种方式更灵活，但也更难控制：任务方向是在推理过程中逐步浮现的，一旦偏了，调试起来非常痛苦。实践中这种方式大多会和 Slot Filling 结合使用。

> [!TIP]
> 面试时我推荐优先回答**做法二**。它的边界清晰、可评估、可调试，更符合工程化思路。

## 为什么需要独立的意图识别

理论上，Agent 完全可以一边思考一边判断用户要做什么（做法三）。但工程实践中，大多数系统还是会选择在主流程之前先做一次独立识别。原因有三个。

### 一、意图决定加载哪套 Prompt / Spec

以电商 Agent 为例，售前和售后两个子域的思考方式截然不同：

| | 售前 | 售后 |
| --- | --- | --- |
| 关注点 | 预算、使用场景、品牌偏好、历史浏览、商品评分、性价比、是否有活动 | 订单状态、是否已发货、是否超过退款期限、是否支持退货、是否需要人工审核、退款路径 |
| Spec | 导购话术、推荐策略 | 售后规则、风控策略 |

显然这是两套完全不同的业务规范。意图识别的第一个作用，就是决定**后面该加载哪一套**。

### 二、意图决定上下文窗口里放什么

同样以电商 Agent 为例：

- **售前**：上下文应重点放入用户画像、价格偏好、历史购买、浏览行为、商品候选集和推荐策略；
- **售后**：上下文应重点放入用户订单、物流状态、售后政策、支付记录和退款记录。

在售后场景里塞一堆用户画像和商品偏好，纯粹是浪费上下文窗口。所以意图识别的第二个作用是决定**当前上下文窗口里应该放什么、不应该放什么**。

### 三、意图决定调用哪个工具

Agent 最终是要调用工具的：

- 商品推荐 → 商品检索工具；
- 订单查询 → 订单系统；
- 退款申请 → 售后系统；
- 内容生成 → 文档生成工具。

意图识别错了，工具调用大概率也会错；更糟的情况是模型根本选不出合适的工具，导致整个流程卡死。

## 提示词怎么写

意图识别提示词的核心目标，是让模型在**一个受控的业务意图空间**里完成分类和结构化输出。说人话就是：给定几个选项，让大模型从中选一个，并按指定格式输出。

### 1. 定义清楚候选意图

这是最重要的一点：**不要让模型自己发明意图，不允许无中生有**。

在识别之后，还可以叠加一层代码校验，进一步兜底。

### 2. 定义清楚意图边界

只列意图名称是不够的，还要解释边界。尤其是两个意图在语义上比较接近的时候，一定要澄清。

比如 `product_recommendation`、`product_comparison`、`product_query` 就经常被混淆，提示词里必须明确说清楚三者的区别：

- `product_query`：用户已经在问某个具体商品的信息；
- `product_comparison`：用户手里已经有候选，要横向对比；
- `product_recommendation`：用户还没有目标，要你帮他挑。

### 3. 定义清楚意图的参数

也就是 Slot Filling 里的 Slot（槽位）。可以进一步说明哪些参数必填、可选参数的默认值是什么。

除了业务参数，还有一些通用参数值得考虑：

```text
must_have_features：必须满足的特性。
nice_to_have_features：加分项。
hard_constraints：硬约束。
soft_preferences：软偏好。
```

### 4. 加入 few-shot

few-shot 不需要很多，关键是覆盖**容易混淆的边界**。

```text
用户输入：“3000 以内有什么手机推荐，主要拍照好一点？”
输出：
{
  "intent": "product_recommendation",
  "slots": {
    "category": "手机",
    "budget_max": 3000,
    "usage_scenario": "拍照",
    "soft_preferences": ["拍照好一点"]
  },
  "need_clarification": false
}
```

如果某些意图确实非常容易搞混，可以在 few-shot 里同时给出**正例和反例**，把边界钉死。

### 意图太多怎么办

如果意图特别多（有些人喜欢把意图切得很碎），把全部意图及其说明都塞进提示词，再叠加上下文，就可能超出大模型的窗口。

解决办法是**层次化意图**：先做粗粒度的域识别（比如售前 / 售后），再在域内做细粒度识别。本质上是一棵决策树，每次只把当前这一层的候选意图喂给模型。

## 识别不出来怎么办

很多系统的问题是：不管用户输入什么，都强行归到某个业务意图上。但真实的用户输入经常是不完整、不清楚，甚至超出系统能力范围的。

所以理论上有两个出口：

- `unsupported`：用户的意图完全不在候选意图中 —— 考虑**拒识**；
- `unclear`：意图之间有混淆，或者参数不够 —— 考虑**澄清**。

### 澄清

假设用户输入"帮我推荐一条裤子"。想让 Agent 效果好，就不要急着立刻推荐，而是先收集关键信息：

```json
{
  "intent": "product_recommendation",
  "slots": { "category": "裤子" },
  "missing_slots": ["price"],
  "need_clarification": true,
  "clarification_question": "你想让我推荐什么价位的裤子呢？"
}
```

> [!NOTE]
> 实践中有些人的理念是：参数不全也先猜一个，尽快给出回答。
>
> 我不赞同。我更倾向于**先收集完整的参数和约束，再回答**。这也是我一贯坚持的观点：好的回答比快的回答，用户体验更好。

### 拒识

比如用户输入"帮我生成一个奥特曼动画"。这个输入不符合候选意图中的任何一个，超出了电商 Agent 的支持范围，这时就应该明确拒绝，而不是硬着头皮去推荐商品。

## 常规的三层识别方案

生产中一般不会只用一种方式，而是分三层逐级升级。

### 第一层：代码

通过代码实现一套简单的意图识别机制，可以是：

- **页面引导**：页面上有个"下一步"按钮，用户点了就执行下一步，直接跳过意图识别；
- **关键字提取 / 正则匹配**：比如用户输入"继续"，意味着要延续上一个意图，或按计划执行下一步；
- **规则引擎**：用户输入或上下文状态命中某条规则时，判定为某个意图，通常依赖输入规范化之后的结果；
- **其他任何能用代码识别的机制**：这件事非常灵活，传统工程手段都可以拿来做这一层。

这一层的特点是：**快、准、便宜、稳定**。尤其对"继续""下一步"这类高频输入，效果奇好。

### 第二层：轻量级大模型

调用各种 Flash、Mini 级别的模型，讲究的是**快和省**。

这一层适合处理那些不适合写死规则、但也不需要深度推理的输入。比如"帮我推荐一个手机"，显然不需要深度推理就能判断。

### 第三层：深度推理大模型

用来兜底复杂场景：

- 表达非常复杂；
- 强依赖上下文；
- 多轮对话中发生意图切换；
- 用户输入包含多个意图；
- 需要根据上下文补全隐含信息。

**为什么不跳过第二层，直接用深度推理模型？**

答案很简单：大多数时候用户的输入和意图都很明确，轻量级模型就能表现得很好——**准确率高的同时，响应速度还快**。为了少数复杂 case 让所有请求都付出高延迟和高成本，不划算。

### 层间怎么路由：置信度

常规做法是让第二层在输出意图时，额外输出一个置信度：

```json
{ "intent": "product_recommendation", "confidence": 0.87 }
```

然后按阈值分流：

| 置信度 | 处置方式 |
| --- | --- |
| > 0.85 | 直接接受 |
| 0.6 ~ 0.85 | 进入仲裁或澄清 |
| < 0.6 | 交给深度推理模型 |

> [!WARNING]
> 阈值不是拍脑袋定的，要根据测试集和线上效果调出来。
>
> 另外，大模型输出的 `confidence` 不一定是真正的概率，它更像一个"自我评分"。实践中最好结合规则命中、向量相似度、历史准确率等信号一起判断。

## Slot Filling：把参数找全

前面说过，意图识别的输出是"意图枚举 + 该意图的参数"。那么问题来了：怎么知道需要哪些参数？又怎么知道这些参数都拿到了？

**Slot Filling（槽位填充）** 就是解决这个问题的：明确告诉模型需要识别哪些参数，并对识别结果做检查。

例如用户输入"帮我推荐一台笔记本，主要是写代码，最好轻一点"，系统应该输出：

```json
{
  "intent": "product_recommendation",
  "slots": {
    "category": "笔记本电脑",
    "usage_scenario": "写代码",
    "soft_preferences": ["轻一点"]
  },
  "missing_slots": ["budget_max"],
  "need_clarification": false
}
```

注意多出来的 `missing_slots` 字段——它记录的是**还缺哪些参数**。

在这个基础上还有一种高级做法：结合上下文，在 ReAct / TAO 循环中逐步补全所有槽位，直到 `missing_slots` 为空。在这种形态下，意图识别不只是找出意图枚举值，还要**把参数找全**。

### 约束：硬约束 vs 软约束

意图识别的参数里，可以单独划分出一类**约束**参数，并进一步分为两种：

- **硬约束**：无论如何都必须满足。比如 AI Coding 时你明确说"不要改动 A 文件"，它就不应该改。
- **软约束**：尽力满足。模型要把它考虑在内，但确实无法满足时可以不满足——不过我建议，没满足时要**明确告知用户**，以提升体验。

相信你用 Coding 工具时一定遇到过：明明说了"不要修改 A 接口"，它还是改了。这会让用户的怒气值急剧上升，对工具的印象大坏。

> [!TIP]
> 面试中主动提及意图识别中的约束处理，并强调**这些约束要贯穿整轮对话**，能为你赢得一些加分。

## 怎么评估效果

### 基础指标：Top-K Accuracy

系统每次返回 K 个候选意图，只要标准答案在这 K 个候选里，就算命中。

比如 K = 3，测试 100 条样本，其中 85 条的标准答案出现在 Top-3 中，那么 Top-3 Accuracy 就是 85%。

实践中更常用的是 **Top-1 Accuracy**：系统输出的第一个意图是否就是标准答案。100 条样本里 88 条第一意图正确，Top-1 Accuracy 就是 88%。

### 需要额外关注的指标

**1. 分意图准确率**

假设系统 80% 的请求都是商品推荐，那模型全部猜"商品推荐"，整体准确率也会很好看。但对于退款、投诉、订单查询这些**低频却重要**的意图，可能识别得很差。

所以整体准确率会骗人，必须拆开看。

**2. 拒识与澄清指标**

- **拒识准确率**：应该拒识的时候，系统是否拒识了；
- **误拒率**：本来能处理，却被错误拒识；
- **漏拒率**：本来应该拒识，却被强行归类；
- **澄清触发准确率**：缺少关键信息时，是否正确追问；
- **澄清后收敛率**：追问之后，用户任务是否顺利推进。

**3. Slot Filling 指标**

- **槽位准确率**：抽取出的槽位值是否正确；
- **槽位召回率**：用户提供的信息有没有被抽出来；
- **必填槽位完整率**：启动流程必需的槽位是否齐备；
- **槽位更新准确率**：多轮对话中，新信息是否正确覆盖旧信息；
- **约束识别准确率**：硬约束和软偏好是否识别正确。

### 准确率多高才算高

面试里有个很难回答的问题：意图识别准确率到底多高才算高？报多少合适？

这里给出一些我收集的参考数据：

- **领域专属 Agent**：尤其是领域小、用户输入规范的，可以做到 **99% 以上**。面试中用这个数据。
- **通用 Agent**：很难做到特别高，Top-1 一般在 **80% ~ 90%** 之间。也有人声称更高，但我怀疑水分比较大——有些 Agent 表现得好像很懂你，输出的东西却驴唇不对马嘴。

> [!TIP]
> 不管你说多高，都会有面试官觉得太高（在吹牛），也会有面试官觉得太低（水平差）。所以关键是：**为"太高"和"太低"都准备好解释**。
>
> **被质疑太高**：可以解释为——你的 Agent 是领域专属的，总共就支持那么几个意图。比如只有"查询订单"和"发起退货"两个意图，那就算什么都不做，只调一次大模型，超过 90% 也轻轻松松；而且用户脑洞没那么大，输入比较简单，内部 Agent 和 toB Agent 更是如此。
>
> **被质疑太低**：可以说目前意图识别做得比较简单，正在计划优化。如果理论知识够扎实，还可以顺势讲讲打算怎么优化。

### 怎么测算：构建测试集

实践中我一般通过**构建测试集**来计算准确率、拒识率等指标。准备 100 个测试用例，80 个输出了预期意图，准确率就是 80%。其他指标同理。

设计测试集时，至少要覆盖以下场景：

| 场景 | 说明 |
| --- | --- |
| 标准表达 | 用户明确说出系统支持的意图，测试最基础的识别能力 |
| 口语化表达 | 模仿用户随意说话：病句、省略、指代。一般要结合输入规范化一起测 |
| 槽位缺失 | 输入缺少意图所需的部分参数，例如缺少价格区间 |
| 拒识 | 应当被明确拒绝的输入 |
| 易混淆样本 | 两个输入很接近，但意图差别很大 |

下面这些场景不是必需的，但我一般也建议覆盖（临时抱佛脚准备面试可以先忽略）：

- **跨轮补充**：用户往往不会一次说完，需要合并多轮对话才能得到完整参数；
- **约束识别**：输入带有硬约束或软约束，要确认被识别出来；
- **意图切换**：多轮对话中从一个意图跳到另一个意图；
- **多意图输入**：用户一次性想做多件事。

如果你的意图识别有特殊机制，也要补上对应的测试用例。可以说，传统软件工程中设计测试用例的技巧，在这里同样适用。

## 小结

意图识别看起来只是"分个类"，实际上它决定了 Agent 后续的一切：

1. **加载哪套 Spec** —— 售前和售后的业务流程完全不同；
2. **上下文里放什么** —— 窗口有限，不能什么都塞；
3. **调用哪个工具** —— 意图错了，工具大概率也错。

工程上成熟的方案是**三层降级**：能用代码规则解决的就用代码（快、准、便宜），剩下的交给轻量级模型（快、省），只有复杂场景才升级到深度推理模型。同时，用 `unsupported` 拒识和 `unclear` 澄清两个出口兜住识别不出来的情况，并用测试集持续度量效果。
